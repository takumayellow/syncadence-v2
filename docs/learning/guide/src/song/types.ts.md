曲データ（`public/songs/<id>.json`）と曲一覧（`public/songs/index.json`）が、どんな形の値なのかを TypeScript の「型」として書き下したファイルです。

## このファイルが担うもの

- 難易度の名前 4 つ（`easy`・`normal`・`hard`・`expert`）と、その表示名を決める（L1-9）。
- 曲データの中身の形を決める。特に大事なのは次の 2 つです。
  - **`MusicEvent`**（L12）: 鳴らすピアノの音 1 つ。`[開始秒, 音高, 長さ秒, ベロシティ, 手]` の 5 つの数の組。
  - **`RawChartNote`**（L15）: 譜面のノーツ 1 つ。`[時刻秒, レーン, ロングノーツの長さ秒, 鳴らす音の添字の列]` の 4 つ組。最後の列が `MusicEvent` の配列の**何番目の音を鳴らすか**を指していて、これが「ノーツと音が必ず一致する」仕組みの要です。
- 曲 1 つ分の全体（`Song`）と、選曲画面用の要約（`SongSummary`）の形を決める（L17-55）。

このファイルには**実行される処理がほとんどありません**。中身はほぼ「この値はこういう形をしている」という宣言で、TypeScript はこれを使って、書き間違い（数のはずの所に文字列を入れる、など）をプログラムを動かす前に見つけます。実行時に JSON の形を本当に確かめるのは `src/song/validate.ts` の仕事です。

## このファイルで初めて出てくる文法

- L1 `[...] as const` と L2 `(typeof X)[number]` — 配列を書き換え不可の決まった値の並びにし、その要素の型を取り出す
- L4 `Record<Difficulty, string>` — 難易度ごとに文字列を持つ表（文法の索引の『Record 型』）
- L11 `/** … */` — 文書コメント
- L12 `readonly [number, number, …]` — タプル型
- L15 `readonly number[]` — 書き換えない数の配列
- L43 `interface A extends B` — 型の継承
- L49 `readonly version: 2` — 数のリテラル型

## 読みどころ

- `MusicEvent`（L12）と `RawChartNote`（L15）。**5 つ組と 4 つ組の各欄が何か**を覚えておくと、`session.ts`・`scheduler.ts`・`engine.ts` の `event[0]`・`note[3]` といった書き方がすぐ読めます。
- `RawChartNote` の 4 番目（鳴らす音の添字の列）。ノーツから音への矢印はこの 1 本だけです。
- `Song`（L48-55）。曲データ JSON の最上位にある欄の一覧になっています。

## 落とし穴

- **型は実行時には消えます。** `readonly` や `version: 2` は、TypeScript が書いたコードを検査するための印で、ブラウザが受け取った JSON の中身を守ってはくれません。外から来た JSON が本当にこの形かは `validate.ts` が 1 つずつ確かめています。
- **時刻の単位は「曲の秒」です。** テンポを落として遊ぶ（再生速度 `rate` を 1 未満にする）と、実際の経過時間は `曲の秒 ÷ rate` になります。この割り算は `session.ts` と `clock.ts` が行い、ここに書かれた数は常に原曲のテンポでの秒です。

> **文法: as const と配列の要素の型**
>
> L1 の `["easy", "normal", "hard", "expert"]` は 4 つの文字列の配列です。普通に書くと TypeScript はこれを「文字列の配列（`string[]`）」とだけ覚え、中身が何だったかは忘れます。
> 末尾に `as const` を付けると、「この配列は**この 4 つの値で、この順番のまま、二度と変わらない**」と覚えさせられます。型は `readonly ["easy", "normal", "hard", "expert"]` になります。
>
> L2 はそこから「要素の型」を取り出す書き方です。内側から順に読みます。
>
> 1. `typeof DIFFICULTIES` — 型を書く場所に置いた `typeof 変数名` は、「その変数の型」を意味します。ここでは上の `readonly ["easy", …]`。
> 2. `( … )[number]` — 配列の型の後ろに `[number]` を付けると、「数の添字で取り出せる要素の型」、つまり**要素の型を全部 `|` でつないだもの**になります。
>
> 結果、`Difficulty` は `"easy" | "normal" | "hard" | "expert"` という型になります（`|` は文法の索引の『型の別名 type と合併型 `|`』）。この型の変数には、この 4 つの文字列のどれかしか入れられません。

難易度の名前を**配列（実行時に使う値）と型（書き間違いの検査に使う印）の両方**として持つための定番の書き方です。値の配列は `validate.ts` の L66 で 4 難易度を順に検査するときや、選曲画面で難易度ボタンを並べるとき（`src/ui/SongSelect.tsx` の L133）に使い、型のほうは「難易度を表す引数には、この 4 つ以外を渡せない」という検査に使います。名前を 1 か所に書くだけで両方がそろうので、難易度を足すときも直すのはここだけで済みます。

`export`（文法の索引の『import と export』）が付いているので、どちらも他のファイルから取り込めます。

> **文法: 文書コメント `/** … */`**
>
> `/*` から `*/` までは複数行に書けるコメントです。特に `/**` で始めたものは「直後の宣言の説明書き」として扱われ、エディタでその名前にマウスを乗せると、この文が表示されます。実行には何の影響もありません。

> **文法: タプル型**
>
> `[number, number, number, number, number]` のように、角括弧の中に型を並べたものを**タプル型**と呼びます。「要素が**ちょうど 5 個**あり、**何番目が何の型か**が決まっている配列」という意味です。普通の配列の型 `number[]`（数がいくつ並んでいてもよい）とは違い、長さと位置ごとの意味が決まっています。
>
> 前の `readonly` は「この配列の中身を書き換えない」という印です。`event[0] = 3` のような代入を書くと TypeScript がエラーにします。（オブジェクトの欄に付ける `readonly` は文法の索引の『interface と readonly』。）
>
> 中身を取り出すときは `event[0]`（0 番目）、`event[1]`（1 番目）… と番号で指します。番号は 0 から数えます。

`MusicEvent` は**鳴らすピアノの音 1 つ**です。L11 の説明書きどおり、5 つの欄は次の意味です。

| 位置 | 中身 | 単位・値 | 作る所（`tools/build_songs.py`） |
|---|---|---|---|
| `[0]` | 鳴り始める時刻 | 曲の頭からの秒 | L64 `score.seconds(n.start)` |
| `[1]` | 音高 | MIDI の音番号。60 が真ん中のド、1 増えるごとに半音上がる | L64 `n.pitch` |
| `[2]` | 鳴っている長さ | 秒。ペダルを踏んでいる間に離した鍵盤は、ペダルを上げるまでの長さ | L64 `score.sounding_end(n)` との差 |
| `[3]` | ベロシティ（打鍵の強さ） | MIDI の 1〜127 | L65 `n.velocity` |
| `[4]` | 手 | 0 = 右手、1 = 左手 | L65 `0 if n.hand == "R" else 1` |

実物の例です。「エリーゼのために」の曲データの最初の音は `[0.0, 76, 0.208, 62, 0]` で、「曲の 0 秒に、音番号 76（ミ）を 0.208 秒、強さ 62 で、右手で鳴らす」と読みます。

曲データの `events` 欄は、この 5 つ組を**時刻の早い順（同じ時刻なら音の低い順）**に並べた配列です。並べているのは `tools/chart.py` の `event_order`（L81-83）で、この順番を前提にしているのが `src/audio/scheduler.ts`（早い順に予約していき、先の音が出てきたらそこで止める）です。添字（配列の何番目か）は、次の `RawChartNote` から音を指す番号としても使われます。

すべての欄が数なのは、JSON を小さくするためです。曲によっては音が 3000 個ほどあり（「幻想即興曲」の曲データでは 3014 個）、`{"time": …, "pitch": …}` のように欄の名前を毎回書くより、位置で意味を決めたほうがずっと短くなります。

`RawChartNote` は**譜面のノーツ 1 つ**です。L14 の説明書きどおり 4 つの欄を持ちます。

| 位置 | 中身 | 単位・値 |
|---|---|---|
| `[0]` | 判定線に届く時刻 | 曲の頭からの秒 |
| `[1]` | レーン | 0 から数えた番号。左端が 0。EASY/NORMAL は 0〜3、HARD/EXPERT は 0〜5 |
| `[2]` | ロングノーツの長さ | 秒。**0 ならふつうのタップのノーツ** |
| `[3]` | 鳴らす音の添字の列 | `events` 配列の何番目の音か、を並べた配列 |

4 番目の欄だけ型が `readonly number[]`（長さの決まっていない、書き換えない数の配列）になっています。和音のように同時に鳴る複数の音を 1 つのノーツに結び付けるためです。

### ノーツと音のつながり

4 番目の欄が、このゲームの設計の中心です。例を 2 つ挙げます（どちらも「エリーゼのために」の EASY）。

- `[29.583, 2, 0.0, [164, 165]]` — 29.583 秒にレーン 2 を叩くタップ。`events[164]` は `[29.583, 65, 0.208, 62, 0]`、`events[165]` は `[29.583, 72, 0.208, 62, 0]` で、同じ時刻に右手で弾く 2 音です。
- `[76.25, 3, 1.19, [507, 508, 509, 510]]` — 76.25 秒から 1.19 秒押し続けるロングノーツ。指す 4 音は音番号 64・67・70・73 の和音で、どれも 76.25 秒から 1.25 秒鳴ります。

ノーツの時刻 `[0]` は、指している音の時刻とまったく同じ値です。どちらも `tools/build_songs.py` が同じ楽譜の同じ音から作るからで、「ノーツと音が合っていない」ということが作りの上で起こりません。

どの音が結び付くかは `tools/chart.py` の `build_candidates`（L86-112）が決めます。**同じ瞬間に同じ手で弾き始める音をまとめて 1 組**にし（L89-91, L96）、その組の全員の添字を `links` にします。右手の組なら旋律のノーツに、左手の組ならベースのノーツになります。

この結び付きは、ブラウザ側で 2 通りに使われます。

1. **キー音モード**（叩いた音だけ鳴らす設定）: `src/game/engine.ts` の L60-63 で、どれかのノーツに結び付いた音の添字を集めて、自動で鳴らす音から外します。代わりに、ノーツを叩いて判定が付いたとき（L129-135）に、`links` の音をその場で鳴らします。結び付いていない音（例えば EASY では拾われない左手の伴奏）は、キー音モードでも自動で鳴り続けます。
2. **検査**: `src/song/validate.ts` の L81 が、添字が `events` の範囲内の整数であることを確かめます。範囲外の添字があると、叩いたときに鳴らす音が無いからです。

ロングノーツの長さ `[2]` は、音の長さ `events[…][2]` とは別の値です。上の例では音が 1.25 秒鳴るのに、ノーツは 1.19 秒です。`tools/chart.py` の `_hold_duration`（L266-273）が、鍵盤を離す位置（ペダルは含めない）か次のノーツの時刻のうち早いほうまでを取り、そこから 0.06 秒（`HOLD_RELEASE_GAP / 2`）引いているためです。長さが難易度ごとの下限に届かない音はタップのノーツ（`[2]` が 0）になります。

名前の `Raw`（生の）は、JSON に書かれたままの形という意味です。ゲーム中は `src/game/session.ts` がこれを、欄に名前の付いた `PlayNote`（session.ts の L6-12）に作り直して使います。

>
> `interface SongSummary extends SongInfo { … }` は、「`SongInfo` の欄を全部持ち、さらに `{ … }` の中の欄も持つ」という意味です。共通の欄を何度も書かずに済みます。

@@ 47-55

> **文法: 数のリテラル型**
>
> `readonly version: 2` の `2` は値ではなく**型**です。「この欄には数の 2 だけが入る」という意味で、`version: number`（どんな数でもよい）より狭い型です。文字列でも同じ書き方ができ、L2 の `"easy" | "normal" | …` も文字列のリテラル型を `|` でつないだものです。

`Song` は**曲 1 つ分のデータ全体**で、`public/songs/<id>.json` の中身そのものです。`SongInfo` の欄に加えて次を持ちます。

| 欄 | 型 | 中身 |
|---|---|---|
| `version` | `2` | 曲データの形式の版。v1 の形式と区別するため。`validate.ts` の L55 が 2 以外を受け付けない |
| `credit` | `Credit` | 楽譜の出どころ（L23-30） |
| `bars` | 数の配列 | 小節線の時刻（秒）。描画で横線を引くのに使う |
| `beats` | 数の配列 | 拍の時刻（秒）。同じく描画用 |
| `events` | `MusicEvent` の配列 | 鳴らす音すべて（L12） |
| `charts` | 難易度 → `ChartData` | 4 難易度の譜面（L17-21） |

`bars` と `beats` は判定には使わず、レーンに小節線・拍線を描くためだけのものです（`src/game/engine.ts` の L207-208 で描画用の値に渡しています）。

1 つの曲データに **4 難易度の譜面と、鳴らす音の列が 1 本だけ**入っている点に注目してください。どの難易度で遊んでも鳴る曲は同じで、難易度によって変わるのは「どの音にノーツを付けるか」だけです。
