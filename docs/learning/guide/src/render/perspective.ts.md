奥から手前へ流れるレーンの「どこに何を描くか」を、画面の大きさと時刻から計算する、絵を 1 枚も描かない計算専用のファイルです。

## このファイルが担うもの

- 画面の幅・高さ・レーン数から、レーンの置き方（奥の端と判定線の高さ、判定線でのレーン全体の幅）を決める `makeTrack`（L39-45）。
- 「判定線に着くまであと何割の時間か」を、画面の奥行き（**深さ**）に変える `depthOf`（L51-56）。ノーツが奥ではゆっくり、手前ほど速く動いて見えるのはこの関数の曲線のおかげです。
- 深さと画面の y 座標を行き来する `yAt`・`depthAtY`（L58-65）と、深さからレーンの横幅・左右の端を出す `spreadAt`・`laneEdge`（L68-76）。
- タッチした x 座標がどのレーンかを決める `laneAtX`（L82-86）。

このファイルでいう「深さ」は 0 が奥の端（`farY`）、1 が判定線（`judgeY`）の、画面の縦の位置を 0〜1 に直した数です。1 より大きければ判定線より手前（画面の下のほう）を指します。

## 読みどころ

- `depthOf`（L51-56）の式は、整理すると **深さ = (1 − u) ÷ (1 + 2u)** になります。u = 0.5（残り時間が半分）でも深さはまだ 0.25 で、残りの 4 分の 1 の時間で一気に手前へ来ます。
- `spreadAt`（L68-70）でレーンの幅は深さの 1 次式で広がり、`yAt`（L58-60）で y も深さの 1 次式です。だから**レーンの左右の線は画面上でまっすぐ**で、奥の 1 点に向かってすぼまります。
- `makeTrack`（L39-45）の 4 つの比率（判定線 0.79、幅 0.79 / 高さの 1.4 倍 / 縦長は 0.94）が画面の骨組みを全部決めています。

## 落とし穴

- **奥の端の 0.04 が 2 つある。** L11 の `FAR_RATIO = 0.04`（奥の端での幅の比）と、L41 の `height * 0.04`（奥の端の y）は別物です。たまたま同じ値なだけで、片方を変えてももう片方は変わりません。
- **先頭のコメントの「比例」は厳密ではない。** L4 は「幅と高さはどちらも深さに比例」と書きますが、幅は `FAR_RATIO + (1 − FAR_RATIO) × 深さ`（L69）で、深さ 0 でも 0 になりません。正確には「深さの 1 次式」です。
- **時刻から深さへの曲線と、レーンのすぼまり方は、同じカメラから計算したものではない。** 詳しくは L47-56 の解説に書きました。見た目の調整として別々に決めた値です。

>
> `/*` から `*/` までと、`//` から行の終わりまでは**コメント**で、プログラムとしては無視されます。人間向けのメモです。
> `/**`（星が 2 つ）で始まるものは、直後に書いた定数や関数の説明として扱われる習慣があり、エディタでその名前にマウスを乗せると説明が表示されます。

> **文法: const による定数**
>
> `const PERSPECTIVE = 2;` は「`PERSPECTIVE` という名前に 2 を入れ、以後入れ替えない」という宣言です。`const` で作った名前に別の値を入れ直そうとするとエラーになります。行末の `;` は文の区切りです。
> 大文字とアンダースコアだけの名前（`FAR_RATIO`）は「調整用の固定値」だと一目で分かるようにする慣習で、文法上の意味はありません。

L1-6 はファイル全体の説明です。ここで言っていることは 2 つです。

1. レーンは、奥の消失点へ向かって細くなる**台形**である。
2. 時刻から深さへは**透視投影**（遠くの物ほど小さく、ゆっくり動いて見える写し方）で写すので、ノーツは奥ではゆっくり、手前ほど速く動いて見える。

ここがノーツの「近づき方」を決める式です。

**入力 u** は「判定線に着くまでの残り時間を、ノーツが流れてくる時間（`approachSeconds`）で割った比」です。呼ぶ側（`src/render/highway.ts` の L132・L163）で `(ノーツの時刻 − 今の曲の位置) / (approachSeconds × 再生速度)` として計算されます。

- u = 1: ちょうど奥の端に現れた瞬間
- u = 0: ちょうど判定線の上
- u < 0: 判定線を過ぎた

L52 で `s(x) = 1 / (1 + 2x)` という小さな関数を作り（文法の索引の『アロー関数』）、L55 で

```
深さ = (s(u) − s(1)) / (1 − s(1))
```

を返します。`s(1) = 1/3` なので、代入して整理すると

```
深さ = (1/(1+2u) − 1/3) / (2/3) = (1 − u) / (1 + 2u)
```

です。`s(0) = 1` なので u = 0 で深さ 1、u = 1 で深さ 0 になるよう、`s(1)` を引いてから `1 − s(1)` で割って 0〜1 にそろえています。

| u（残り時間の比） | 深さ | レーンの幅の比（`spreadAt` ÷ `nearWidth`） | pjsekai の値 |
|---|---|---|---|
| 1 | 0 | 0.040 | 0.073 |
| 0.75 | 0.1 | 0.136 | 0.140 |
| 0.5 | 0.25 | 0.280 | 0.270 |
| 0.25 | 0.5 | 0.520 | 0.519 |
| 0 | 1 | 1.000 | 1.000 |
| −0.1 | 1.375 | 1.360 | — |
| −0.3（下限） | 3.25 | 3.160 | — |

右の 2 列は、`docs/research/05-ui-references.md` の 1.2 節で、pjsekai エンジンの `1.06 ^ (45 × (p − 1))` と比べた表と同じ値になります（レーンの幅の比は L69 の式で計算し直しました）。奥の端を除けば差は 0.02 以下で、この曲線はプロセカの流れ方とほぼ同じです。

**なぜこの形だと「奥でゆっくり、手前で速い」のか。** 時間が等しく進んでも、深さの増え方は一定ではありません。u が 1 → 0.75（最初の 4 分の 1）で深さは 0 → 0.1 しか進まないのに、0.25 → 0（最後の 4 分の 1）では 0.5 → 1 と半分を一気に進みます。

`1/(1+2u)` は、物までの距離が `1 + 2u` のとき画面上の大きさが距離に反比例する、という透視の式の形です。u = 1 の奥の端は判定線の 3 倍遠くにある、と見なしていることになります。

**L54 の下限 −0.3 の理由。** `1 + 2u` は u = −0.5 で 0 になり、割り算が壊れます（L53 のコメントの「発散」）。u を −0.3 で止めると深さは 3.25 で、判定線（深さ 1）より手前、画面の下の端（深さ 1.28、次の範囲で計算します）よりずっと外です。止めた所はもう画面に映らないので、見た目は変わりません。

**時刻の曲線と、レーンのすぼまり方は別々に決めている。** L55 の式をカメラで考えると、奥の端は判定線の 3 倍遠いので、レーンの幅は奥の端で 3 分の 1 になるはずです。ところが L69 は奥の端の幅を 4%（`FAR_RATIO`）にしています。つまりこのファイルは「ノーツの動く速さ」と「レーンの形」を 1 台のカメラで計算しているのではなく、それぞれ見た目で選んだ値を組み合わせています。

深さと画面の y の変換です。どちらも 1 次式で、互いに逆の計算になっています。

- `yAt`（L58-60）: `farY + (judgeY − farY) × 深さ`。深さ 0 で `farY`、1 で `judgeY`。
- `depthAtY`（L63-65）: `(y − farY) / (judgeY − farY)`。`yAt` を y について解いたもの。

1920×1080 なら `judgeY − farY` は 853.2 − 43.2 = 810 px で、深さが 0.1 増えると 81 px 下へ行きます。

画面の下の端（y = 1080）の深さは `depthAtY` で (1080 − 43.2) / 810 = **1.28** です。`farY = 高さ × 0.04`、`judgeY = 高さ × 0.79` なので、高さが 200 px 以上ならどの画面でも (1 − 0.04) / (0.79 − 0.04) = 0.96 / 0.75 = 1.28 になります。`src/render/highway.ts` の L410 がこの値（`bottomDepth`）を計算し、レーンを画面の下の端まで伸ばすのに使います。

`depthAtY` は、深さを先に決められない物（判定線の帯の上下の端、キーの文字の位置、コンボの数字の高さ）を、y から逆にたどってレーンの幅を知るために `src/render/highway.ts` で使われます。

レーンの左右の位置です。

**`spreadAt`（L68-70）** はレーン全体の幅で、

```
幅 = nearWidth × (0.04 + 0.96 × 深さ)
```

深さ 0（奥の端）で `nearWidth` の 4%、深さ 1（判定線）でちょうど `nearWidth`、深さ 1.28（画面の下の端）で 1.2688 倍です。

**`laneEdge`（L73-76）** は、深さ `depth` でのレーン番号 `lane` の**左の線**の x です。

1. L74 その深さでの全体の幅 `spread` を出す。
2. L75 全体の左の端 `centerX − spread / 2` から、1 本分の幅 `spread / lanes` を `lane` 本ぶん右へ進める。

`lane = 0` なら全体の左の端、`lane = lanes`（4 レーンなら 4）なら全体の右の端になります。L72 のコメントの「右端の外側の線」はこのことです。レーン `i` の右の線は `laneEdge(track, i + 1, depth)` で求めます。

**レーンの線は画面上でまっすぐ。** `yAt` も `spreadAt` も深さの 1 次式なので、ある線の x と y はどちらも深さに比例して動き、画面上では 1 本の直線になります。全部の線をさらに奥へ伸ばすと、幅が 0 になる深さ `−0.04 / 0.96 ≈ −0.042`、1920×1080 なら y ≈ 43.2 − 0.042 × 810 ≈ 9.5 px の所で 1 点に集まります。これが消失点です。

研究メモ（`docs/research/05-ui-references.md` 1.1 節）の pjsekai は、消失点を y = 0 に置いて「レーンの x = レーンの位置 l × y」と書きます。このファイルの式も、y を消失点から測り直すと

```
x − centerX = (lane / lanes − 1/2) × nearWidth × 0.96 × (深さ + 0.042)
```

となり、「横の位置 = レーン上の位置 × 消失点からの高さ」という同じ形です。違いは消失点を画面の中（上の端から約 9.5 px）に置いていることだけです。

2. L84 そこから何本分右にあるかを、判定線での 1 本の幅 `nearWidth / lanes` で割って `Math.floor` で切り捨てる（L34-45 の「Math の関数」）。たとえば 1920×1080・4 レーンで左の端は 960 − 756 = 204 px、1 本の幅は 378 px なので、x = 700 なら (700 − 204) / 378 ≈ 1.31 で、レーン 1（左から 2 本目）です。

**高さを見ていない**のが要点です。レーンは奥ほど細いので、本当は y によってレーンの境目の x がずれます。それでも判定線での幅だけで決めるのは、L79-80 のコメントのとおり、指は判定線の近くを叩くので、高さによって当たる範囲が細くならないようにするためです。端のレーンを画面の端まで広げるのも同じ理由です（研究メモ 1.4 節。pjsekai は縦の範囲も区切るが、v2 は画面全体で受け付ける）。
