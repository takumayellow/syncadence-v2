Mutopia Project から曲ごとの楽譜（LilyPond の `.ly`）と MIDI を取ってきて、楽譜のヘッダに「Public Domain」と書かれていない曲を止める、取り込みの入口のファイルです。

## このファイルが担うもの

- 曲の目録 `tools/songs.json` を読み、曲 ID と Mutopia 上のパスが安全な文字だけでできているかを確かめる（`load_catalog`、L32-39）。
- Mutopia の配布サーバ（`https://www.mutopiaproject.org/ftp/`）からだけ `.ly` と `.mid` を取る（`download`、L42-47 と `fetch_song` の L60-64）。
- `.ly` のヘッダに `license = "Public Domain"` か `copyright = "Public Domain"` があるかを確かめ、無ければ例外で止める（L66-68）。
- 出どころの URL、浄書者、底本、ファイルの SHA-256、確認日を `sources/mutopia/<曲ID>/meta.json` に書く（L70-87）。

ここで取ったファイルを、`tools/build_songs.py` が譜面と音のデータに変えます。手で 1 回動かす道具で、ゲームの実行中には動きません。

## 呼ぶ・呼ばれる

| 向き | 相手 | 何のために |
|---|---|---|
| 呼ばれる | 人がコマンドで `python tools/fetch_sources.py [--force]` | 曲を増やしたとき、取り直したいとき（docs/design.md の 9 節） |
| 読む | `tools/songs.json` | 曲 ID・Mutopia の ID・パス |

| 読まれる | `tools/build_songs.py` の L30・L79、`tools/tests/test_chart.py` | `meta.json` からファイル名と、画面に出すクレジット（浄書者・ライセンス）を取る |

## なぜ Mutopia の Public Domain の楽譜だけを使うのか

曲の権利は層に分かれています（docs/research/04-assets-and-licenses.md の 1 節）。

| 層 | このゲームでの扱い |
|---|---|
| 作曲 | 作曲者の死後 70 年で切れる。収録曲の作曲者で最も遅いサティ（1925 年没）でも切れている |
| 楽譜データ（浄書・入力した人の仕事） | **ここを確かめる必要がある。** このファイルの検査はこの層のためのもの |
| 録音・演奏 | 使わない。音は楽譜から合成する |
| ピアノの音源 | CC0 の FreePats を使う（`tools/build_samples.py`） |

Mutopia の楽譜は曲ごとにライセンスが違い、Public Domain のほかに CC 系（表示や継承の条件が付くもの）もあります。Public Domain だけに絞れば、楽譜から作った譜面や曲データに条件が付かず、「権利の確認が楽譜の版だけで済む」（docs/design.md の 1 節）。※ 推測: CC 系を受け入れると、条件の確認と表示を曲ごとに管理する手間が増えるので、最初から入口で断る形にしたと考えられます。

この検査は**通らなければ止まる**側に倒してあります。ヘッダが見つからない、綴りが違う（`Public domain` など）、といった場合はすべて失敗になり、曲は取り込まれません。

## 落とし穴

- **検査に落ちてもファイルは残る。** `.ly` と `.mid` は L63 で先に保存され、検査（L67）はその後です。落ちた曲のフォルダには `.ly` と `.mid` があって `meta.json` が無い状態になり、`build_songs.py` はその曲の `meta.json` を読もうとして（L79）止まります。
- **1 曲が落ちると、後の曲は取られない。** L68 の例外をどこも受け止めないので、`main` のループ（L95）がそこで終わります。
- **既にあるファイルは中身を確かめ直さない。** `--force` を付けない限り、ローカルにあるファイルをそのまま使い（L62）、そのハッシュを記録します。前回の取得と同じ中身かどうかは比べていません。
- **`verifiedOn` は実行した日になる。** ファイルを取り直さなかったときも L85 で今日の日付が書かれるので、実行するたびに `meta.json` に差分が出ます。
- **ヘッダの検査はファイル全体が対象。** L28 の `re.MULTILINE` によって「どこかの行頭に `license = "Public Domain"` がある」で通るので、`\header { … }` の中かどうかまでは見ていません。

> **文法: 正規表現と生文字列 `r"…"`**
>
> `re.compile(パターン)` は、文字列の「形」を表す**正規表現**を、何度も使える検査器にしておく関数です。`.match(文字列)` は先頭から形に合うかを、`.search(文字列)` はどこかに合う部分があるかを調べ、合えば一致の情報（`Match`）、合わなければ `None` を返します。
>
> 文字列の前の `r` は「生文字列」の印で、`\` を特別扱いしません。正規表現では `\s`（空白）や `\-`（ハイフンそのもの）のように `\` を多用するので、ふつうの文字列だと `\\s` と二重に書く必要があり、それを避けるためです。

4 つのパターンを分解します。

**`SAFE_PATH`（L26）** — Mutopia 上のフォルダのパス用。

1. `^` 先頭から
2. `[A-Za-z0-9_\-]+` 英数字・`_`・`-` が 1 文字以上（`+` は「1 回以上」）
3. `(/[A-Za-z0-9_\-]+)*` 「`/` と同じ文字の並び」の組が 0 回以上（`*` は「0 回以上」）
4. `$` 末尾まで

`.` が使えないので `..`（上のフォルダへ戻る）は書けず、`/` で始めることも終えることもできません。例 `BeethovenLv/WoO59/fur_Elise_WoO59` は通ります。

**`SAFE_ID`（L27）** — 曲 ID 用。英小文字・数字・`-` だけ。曲 ID は保存先のフォルダ名（L57）と、ブラウザが読む `public/songs/<id>.json` の名前になります。ブラウザ側の `src/song/validate.ts` も同じ形（docs/design.md の 3 節では `^[a-z0-9-]{1,64}$`）を確かめます。

**`PD_HEADER`（L28）** — Public Domain の宣言。

1. `^\s*` 行頭と、0 個以上の空白（字下げ）
2. `(license|copyright)` `license` か `copyright`（`|` は「または」）
3. `\s*=\s*` 空白をはさんだ `=`
4. `"Public Domain"` この綴りそのもの（大文字小文字も区別）

`re.MULTILINE` を付けると、`^` が「文字列全体の先頭」ではなく「各行の先頭」を意味するようになります。`.ly` のヘッダは `\header { … }` の中に 1 行ずつ `title = "…"` の形で並ぶので、行ごとに見る必要があります。

`copyright` も受け付けるのは、Mutopia の古い版の楽譜が `copyright = "Public Domain"` と書くためです（docs/research/04-assets-and-licenses.md の 2 節）。収録 12 曲のうち、たとえば `arabesque-1` や `clair-de-lune` は `copyright`、`fur-elise` や `gymnopedie-1` は `license` の形です。`fur-elise` には `copyright = \markup { … }` という行もありますが、`=` の後が `"Public Domain"` ではないのでこちらは一致せず、`license` の行で通ります。

**`HEADER_FIELD`（L29）** — `re.compile` していない、ただの文字列です。`{name}` の所に後で項目名を入れて（L51）使います。`"([^"]*)"` の `( )` は「この部分を取り出す」印（グループ）で、`[^"]*` は「`"` 以外の文字が 0 個以上」。つまり引用符の中身を取り出します。

>

> **文法: `raise` による例外**
>
> `raise ValueError("…")` は、処理をその場で打ち切り、エラー（例外）を呼び出し元へ投げます。受け止める処理（`try` / `except`）がどこにも無ければ、プログラムはエラーの説明を表示して止まります。`ValueError` は「値が不正」、L68 の `RuntimeError` は「実行中の一般的な異常」を表す、標準の例外の種類です。

> **文法: `None` と条件式 `A if 条件 else B`**
>
> `None` は「値が無い」を表す特別な値で、型注釈 `str | None` は「文字列か、値が無いか」です。
>
> `match.group(1) if match else None` は、`match` が真（一致があった）なら `match.group(1)`、偽（`None`）なら `None`、という 1 行の if です。評価の順は **条件 → 選ばれた側**で、選ばれなかった側は計算されません。`match` が `None` のときに `match.group(1)` を呼ぶとエラーになるので、この順序が大事です。

`header_field` は `.ly` のヘッダから、指定した項目の値を取り出します。

1. `HEADER_FIELD.format(name=name)` で、L29 の `{name}` を項目名に置き換える。`name="maintainer"` なら `^\s*maintainer\s*=\s*"([^"]*)"` になる。
2. `re.search(…, ly_text, re.MULTILINE)` で、行頭からその形の行を探す。
3. 見つかれば `group(1)`（L29 の `( )` で囲んだ部分＝引用符の中身）を返す。

L75-76 で浄書者（`maintainer`）と底本（`source`）を取るのに使います。`fur-elise` ならそれぞれ `Stelios Samelis` と `Breitkopf & Härtel, 1888` です。項目が無い楽譜では `None` が返り、`meta.json` には `null` と書かれます。
